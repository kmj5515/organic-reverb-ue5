## 3. 핵심 설계 결정

### 3.1 물리 모델 — 결합 공간 확산 음장 (Coupled-room diffuse field)
v0는 "에너지 양의 차이 × 임의 계수(DiffusionRate) / (1+거리)"라는 경험식이었다. v1은 확산 음장 이론 한 가지에서 흡음과 전파를 함께 유도한다.

- 방마다 에너지 밀도 `w = E / V` (확산 음장 가정)
- 확산 음장에서 면적 S인 면을 통과하는 에너지 흐름 = `c · w · S / 4`
- **흡음**: `dE/dt = -(c·A / 4V)·E`, A = S·α → 이걸 풀면 `RT60 = 0.161·V/A`, 즉 **Sabine 식이 그대로 나온다**
- **포탈**: 순 흐름 = `G·(w_A − w_B)`, `G = c·S_portal·τ / 4` (τ = 문 열림 정도 0~1)
  → 열린 개구부는 흡음계수 1인 면과 같다. 튜닝 상수가 사라지고 물리량(면적·부피·재질)만 남는다.

`FPortal::Distance`는 제거했다. 이 모델에서는 감쇠가 부피 확산으로 자연스럽게 생기므로 필요 없다. 전파 지연 용도로는 5단계에서 다시 검토한다(§5).

### 3.2 적분 방식 — 무조건 안정
| 항목 | 방식 | 성질 |
|---|---|---|
| 흡음 | `E *= exp(-k·h)` 해석해 | dt 크기와 무관하게 정확 |
| 포탈 | 두 방 사이 밀도차가 `exp(-λh)`로 줄어드는 해석해를 포탈마다 적용 | 에너지 정확히 보존, 음수·진동·과보정 없음 |
| 분할 | 흡음 h/2 → 포탈 정방향 h/2 → 포탈 역방향 h/2 → 흡음 h/2 | 포탈 적용 순서에 따른 편향 감소 |
| 서브스텝 | dt > 1/60 s이면 분할 (최대 16회) | 정확도용일 뿐, 안정성과는 무관 |

프레임 드랍(dt 0.2~2 s)에도 발산하지 않으므로 게임 스레드 틱 주기를 자유롭게 바꿀 수 있다(예: 20 Hz 틱으로 예산 절감).

### 3.3 방 인식 — 완전 자동, 복셀 기반 (확정)
6방향 레이 프로브는 L자 방·열린 공간·복도 구분에서 깨지므로 버리고, **점유 격자(복셀) 분할** 방식을 쓴다.

| 단계 | 위치 | 내용 |
|---|---|---|
| 1. 점유 격자 생성 | Unreal 어댑터 | 레벨 영역을 격자(기본 50 cm)로 나누고 칸마다 오버랩 테스트 → 빈 공간 / 벽. 벽 칸은 Physical Material → 흡음계수 기록 |
| 2. 공간 분할 | **Core** (`AcousticSpaceSegmenter`, 신규) | 빈 칸 flood fill → 거리 변환으로 좁은 목(문/개구부) 검출 → 목을 경계로 방 분할 |
| 3. 그래프 생성 | **Core** | 방 부피 = 칸 수 × 칸 부피, 표면적/재질 = 벽과 맞닿은 면, 포탈 면적 = 방 사이 경계 면 수 × 면 면적 |

- 분할 알고리즘이 Core에 있으므로 3단계와 똑같이 콘솔에서 합성 격자(L자 방, 복도+옆방)로 먼저 검증한다. → **구현·검증 완료** (`AcousticSpaceSegmenter.h`, §4.3)
- 문 개폐(τ)는 문 액터가 자신이 걸친 포탈을 찾아 런타임에 갱신한다.
- 파괴 가능한 벽 등 지형 변화 시 해당 영역만 재스캔하는 부분 갱신은 5단계 이후 검토.

### 3.4 리버브 파라미터 매핑 (`FReverbParams`)
| 출력 | 산출식 | UE 대상 |
|---|---|---|
| DecayTime | 리스너 방 Mid 대역 Sabine RT60 | `FReverbSettings::DecayTime` |
| DecayHFRatio | RT60(High) / RT60(Mid) | `DecayHFRatio` |
| ReflectionsDelay | 평균 자유 행로 `4V/S` / c | `ReflectionsDelay` |
| WetLevel | 밀도의 dB 스케일 (기준 0 dB → 1, −60 dB → 0) | Submix Send / `Volume` |

v0의 `Total / 100` 선형 매핑은 청감(로그)과 맞지 않아 dB 매핑으로 바꿨다.

### 3.6 음원별 전파 — Occlusion / Obstruction / Exclusion (5단계)
전역 리버브 하나로는 "벽 너머 소리가 그대로 들린다"는 문제를 해결할 수 없어, 음원마다 리스너까지의 전파를 계산한다 (`AcousticPropagation.h`, 엔진 독립).

| 요소 | 모델 | 게임 출력 |
|---|---|---|
| 직접음 경로 | 같은 방 또는 열린 문 너머 직선 가시 → 손실 없음. 아니면 문 중심을 노드로 한 최단 경로(Dijkstra): 거리 손실 `20·log10(d/d_path)` + 회절 `θ/π × {6, 12, 20} dB` + 문 투과율 `10·log10(Πτ)` | 볼륨 배율 |
| 벽 투과 | 직선이 지나는 벽 수(격자에서 셈) × `{20, 35, 50} dB`, 문 경로와 에너지로 합산. 문이 모두 닫히면 이것만 남음 → Occlusion | 볼륨 배율 |
| 고음 손실 | High가 Mid보다 더 깎인 양 → 로우패스 (0 dB → 20 kHz, 24 dB → 400 Hz, 로그 보간) | 로우패스 |
| 잔향 결합 | 음원 방에 연속 출력을 넣었을 때 정상 상태 밀도 비 `w_L / w_S` (켤레 기울기법, 음원 방별 캐시) → Exclusion | Reverb Submix Send 배율 |
| 들리는 방향 | 리스너 쪽 마지막 문 위치 (계산만, 공간화 적용은 추후) | — |

Unreal: `UOrganicSoundSourceComponent`가 서브시스템에 등록되면 매 틱 경로를 계산해 볼륨·로우패스·Send를 적용한다 (0.1 s 스무딩). 문 상태가 바뀌거나 재스캔하면 잔향 결합 캐시를 무효화한다.

콘솔 검증 (`PropagationTests.cpp`, 방 5×4×3 m, 문 1×2 m):

| 상황 | 결과 |
|---|---|
| 문을 돌아서 옴 | Low / Mid / High = −1.5 / −2.8 / −4.3 dB, 소리 위치 = 문 |
| 열린 문 너머 직선 | 0 dB |
| 문 반쯤 열림 | 열림 대비 정확히 −3.0 dB |
| 문 닫힘 (벽 1개) | −20 / −35 / −50 dB → 볼륨 0.018, 로우패스 1.7 kHz |
| 방 3개 지그재그 | 문 1개 −4.3 dB → 문 2개 −8.4 dB. 모두 닫으면 벽 1개 −35 dB, 벽 2개 −60 dB(하한) |
| 잔향 결합 | 옆방 −4.7 dB, 두 칸 −8.5 dB, 문 닫힘 −60 dB, 30 m 홀 분할 조각끼리 −2.4 dB |

게임 모드 검증 (`ORS_WallTest`, 8×6×3 m 방 두 개, 벽 한쪽 끝에만 문): 옆방 음원 → "문을 돌아서 옴, 문 1개, 벽 1개, 직접음 −5.1 dB (High −7.7), 로우패스 13 kHz, 잔향 Send −5.7 dB". 문에서 약 58° 꺾이는 경로로, 손 계산(회절 −3.9 dB + 거리 −1.2 dB)과 일치.
관찰: 문 모서리를 돌아오는 소리가 −5 dB 정도로 막힘이 약하다. 회절 계수는 청취 튜닝(5-6)에서 올릴 후보.

**한계:** 같은 방 안의 장애물(기둥 등)에 의한 Obstruction은 다루지 않는다 (방 단위 모델). 회절 손실 계수와 벽 투과 손실은 문헌 대표값 수준의 고정값이라 청취 튜닝 대상이다.

### 3.8 원거리 총성 — 거리감 (5-7)
사실적인 총소리의 핵심은 거리감이다. `RenderShot`(`AcousticShotRender.h`, 엔진 독립)이 전파 경로와 잔향 결합으로 다음 단서를 만든다.

| 단서 | 모델 |
|---|---|
| 도착 지연 | 소리가 지나온 거리 / 343 m/s (문을 돌아오면 경로 길이, 벽을 뚫고 오면 직선 거리) |
| 들리는 위치 | 문을 돌아오면 리스너 쪽 마지막 문, 아니면 음원 |
| 직접음 크기 | InnerRadius(5 m) 밖에서 거리 2배당 −6 dB + 공기 흡수 {0.001, 0.005, 0.025} dB/m + 경로 손실(회절/차폐) |
| 로우패스 | 고음이 중음보다 더 깎인 만큼 |
| 녹음 레이어 | 근거리 / 원거리 녹음을 10 ~ 50 m에서 동일 파워 크로스페이드 |
| 직접음 : 잔향 | 잔향은 방 안 어디서나 같으므로(확산 음장) 거리와 무관하게 잔향 결합만큼. 멀수록 직접음만 줄어 "탕" → "쿠웅" |

콘솔 검증 (`ShotRenderTests.cpp`): 20 m → 지연 58 ms / −12 dB, 40 m → 117 ms / −18 dB / 원거리 레이어 우세, 300 m → 고음 추가 −6 dB / 로우패스 7.5 kHz, 모퉁이 너머 → 문 쪽에서 들리고 같은 거리 탁 트인 경우보다 작고 먹먹함, 벽 너머 → −40 dB / 1.7 kHz.

**Unreal 연결에서 확인한 엔진 동작 (UE 5.8 소스):** `AudioMixerSourceManager`는 PreDistanceAttenuation Send 버퍼를 볼륨 적용 전 원본 PCM으로 채우지만, `UAudioComponent::SetSubmixSend`는 단계를 고를 수 없고 항상 PostDistanceAttenuation(볼륨 적용 후)로 보낸다. 그래서 직접음 볼륨을 낮추면 잔향 Send도 같이 낮아진다.
→ 총성은 엔진 거리 감쇠를 끄고(`bAttenuate = false`, 공간화만 유지) 거리감을 볼륨에 직접 넣은 뒤, Send를 `기본 Send × 잔향 결합 ÷ 직접음 볼륨`(0~1 클램프)으로 보정한다. 직접음이 약 −20 dB 이하가 되면 클램프 때문에 잔향도 줄기 시작한다 (한계).
재생 전에 로우패스와 Send를 설정해야 첫 트랜지언트부터 적용되므로, 오디오 컴포넌트를 직접 만들어 설정한 뒤 `Play()` 한다. 도착 지연은 월드 타이머로 예약한다.

게임 모드 검증 (`ORS_DistantGunshot`: 대기실 → 30 m 복도 → 모퉁이 → 20 m 복도 끝 총기):
`path 47.5 m, delay 139 ms, direct −33.3 dB (High −43.3), LPF 3.9 kHz, reverb coupling −20.8 dB → send 0.63`.
손 계산: 직선 거리 감쇠 −16 dB + 돌아가는 거리 −3.6 dB + 모퉁이·문 회절 약 −12 dB + 공기 흡수 −0.2 dB ≈ −32 dB (일치).

튜닝 관찰:
- 약 50 m 밖 원거리 총성이 −33 dB로, 물리적으로는 맞지만 게임에서는 작을 수 있다 → `GunshotInnerRadius`, 회절 계수로 조정 (청취 튜닝 5-6).
- 경로에 복도 분할 조각 사이의 가상 경계까지 포탈로 포함되어 곧은 복도에서도 작은 회절 손실이 붙었다 → **6-2에서 경로 당기기로 해결** (§3.10).

### 3.7 감쇠 측정 도구 (5-4)
결합 공간의 이중 기울기 감쇠를 "테스트 로그"가 아니라 게임 안에서 보여주기 위한 디버그 도구 (`AcousticDecayMeter.h`, 엔진 독립).
`ors.Shot`을 입력하면 리스너 위치에서 테스트 총성을 쏘고, 그 방의 에너지 밀도(Mid)를 매 틱 기록해 실내 음향 표준 지표를 잰다.

| 지표 | 구간 | 의미 |
|---|---|---|
| EDT | 피크 → −10 dB × 6 | 사람이 느끼는 잔향 길이 |
| T20 | −5 → −25 dB × 3 | 실측에서 쓰는 표준 값 |
| Late | −40 → −60 dB × 3 | 후기 꼬리. 옷장+홀처럼 −38 dB 근처에서 꺾이는 곡선도 꺾인 뒤만 재도록 −40 dB부터 |

후기 RT가 EDT의 1.5배를 넘으면 `DOUBLE SLOPE`로 표시한다. 화면 좌하단에 감쇠 곡선 그래프(0 ~ −60 dB)와 지표를 그리고(`UDebugDrawService` 캔버스), 측정이 끝나면 로그로 남긴다.

콘솔 검증 (`DecayMeterTests.cpp`):

| 상황 | EDT | T20 | Late | 판정 |
|---|---|---|---|---|
| 콘크리트 방 하나 (Sabine 4.23 s) | 4.23 s | 4.23 s | 4.23 s | 단일 기울기 |
| 카펫 옷장 + 콘크리트 홀 (옷장 0.37 s / 홀 9.70 s) | 0.31 s | 0.32 s | 9.48 s | **이중 기울기** |
| 옆방에서 난 소리 | 피크 0.14 s 늦게 도착 | — | — | — |

(기준 RT60은 6-1 이후 공기 흡음을 포함한 값이다. 적용 전에는 각각 4.81 s / 13.4 s였다)

게임 모드 검증 (`-ExecCmds="ors.Shot"`, 공기 흡음 적용 후 재측정): `ORS_MaterialComparison` 콘크리트 방 EDT / T20 / Late 모두 1.92 s (방 계산값 1.92 s와 일치, 적용 전 2.03 s), `ORS_ClosetAndHall` 홀 EDT 6.93 s, T20·Late 9.15 s (방 계산값 9.35 s — 옷장과 바깥 문으로 새는 만큼 약간 짧음. 적용 전에는 각각 12.31 / 12.39 / 12.76 s).

### 3.9 공기 흡음 (6-1)
지금까지는 벽에서만 에너지를 잃는다고 봤다. 실제로는 공기 자체가 소리를 먹고(점성·열전도·분자 이완), 잔향은 벽에 닿을 때까지 수백 m를 돌아다니는 소리라 이 손실이 쌓인다. 흡음 면적에 **4mV 항**을 더하는 것으로 표현한다.

$$RT_{60} = \frac{0.161\,V}{A + 4mV}, \qquad k = \frac{c\,A}{4V} + c\,m$$

감쇠율 쪽에서 보면 **방 크기와 무관한 상수 c·m**이 더해지는 것이다. 벽 항 c·A/4V는 큰 방일수록 작아지므로, 공기 항은 큰 공간에서 지배적이 된다. 기존 지수 해석해 적분이 그대로 성립해서 안정성·보존 성질은 건드리지 않는다.

계수는 `AirAbsorption::Coefficient()`(`AcousticTypes.h`) 한 곳에 있다. 원래 원거리 총성(§3.8)이 쓰던 dB/m 상수(ISO 9613-1, 20 °C · 습도 50 %)를 에너지 계수 m = (dB/m)·ln(10)/10 로 환산한 것이라, **직접음과 잔향이 같은 공기를 쓴다**.

| 적용 지점 | 파일 | 방식 |
|---|---|---|
| 에너지 감쇠 시뮬레이션 | `AcousticDiffusionSimulator.h` | `FDiffusionSettings::AirAbsorptionCoefficient` (대역별) |
| 리버브 파라미터 | `ReverbParameterMapper.h` | `FReverbMappingSettings::AirAbsorptionCoefficient` |
| 잔향 결합 (Exclusion) | `AcousticPropagation.h` | 정상 상태 행렬 대각합에 c·m·V 추가 (Mid) |
| 직접음 (원거리 총성) | `AcousticShotRender.h` | 이전부터 적용 중 (dB/m) |

Unreal 쪽은 `AOrganicReverbVolume::AirAbsorptionScale`(1 = 실측값, 0 = 끔)로 네 곳에 같은 배율이 걸린다. 건조/습한 공기를 흉내내거나, 게임적으로 잔향을 더 남기고 싶을 때 줄이면 된다.

검증:

| 대상 | 벽 흡음만 | 공기 흡음 포함 |
|---|---|---|
| 30 x 30 x 10 m 콘크리트 홀 RT60(Mid) | 16.10 s | 11.02 s (−32 %) |
| 같은 홀 HF Decay Ratio | 0.75 | 0.40 |
| 5 x 4 x 3 m 콘크리트 방 RT60(Mid) | 3.43 s | 3.12 s (−9 %) |
| 30 m 홀 대각선 조각끼리 잔향 결합 | −2.41 dB | −3.28 dB |

콘솔 테스트 `Core_AirAbsorption_MatchesSabineFourMVTerm`은 시뮬레이터가 그 RT60 시점에 정확히 −60.000 dB에 닿는지(=적분과 공식의 일치)와, 계수를 0으로 두면 예전 순수 Sabine 거동으로 정확히 되돌아가는지를 함께 본다.

**남은 문제:** Sabine 식 자체의 한계(α > 0.3에서 RT60 과대평가)는 그대로다. Eyring 식 옵션은 적용하지 않았다.

### 3.10 경로 당기기 — string pulling (6-2)
직접음 경로는 Dijkstra로 찾은 **문 중심을 모두 지나는 꺾은선**이었다. 문제는 긴 공간을 `MaxRoomLength`로 쪼갤 때 생긴 "가상 경계"도 포탈이라는 점이다. 실제로는 아무것도 막고 있지 않은데 그 중심을 억지로 지나느라 경로가 조금 길어지고, 꼭짓점마다 회절 손실이 붙었다 (§3.8 튜닝 관찰).

해결은 내비게이션 메시에서 쓰는 것과 같은 **string pulling**이다. 팽팽한 실을 당기면 불필요한 꺾임이 펴지는 것처럼, 앞 꼭짓점에서 격자 가시선(`CountWallsBetween == 0`)으로 직접 보이는 가장 먼 꼭짓점까지 건너뛴다. 막히는 순간 멈추므로 벽을 뚫고 지름길을 내지 않는다.

- 길이와 꺾임 각도는 **당긴 꺾은선**으로 계산한다 (`FPropagationPath::PathPoints`).
- **문 목록(`Portals`)은 건드리지 않는다.** 반쯤 닫힌 문의 투과율 τ는 꼭짓점이 펴져도 그대로 곱해진다 — 기하학적으로 곧더라도 그 문을 통과한 사실은 변하지 않기 때문.
- 디버그 표시도 같은 꺾은선을 그리므로, 화면에 보이는 선이 곧 계산에 쓰인 경로다.

검증 (`Prop_StringPulling_*`, ㄱ자 36 m + 16 m 복도를 12 m로 분할):

| | 꼭짓점 | 경로 길이 | 회절 손실(High) |
|---|---|---|---|
| 당기기 없음 | 5개 | 43.63 m | −11.8 dB |
| 당기기 적용 | 4개 | 43.62 m | −11.5 dB |

게임 모드 A/B (`ORS_DistantGunshot`, 같은 발사 지점): 직접음 −33.3 → **−33.1 dB**, High −43.3 → **−43.0 dB**, 로우패스 3946 → **4028 Hz**. 지그재그 배치처럼 진짜로 막힌 꺾임은 하나도 펴지지 않는다(`Prop_StringPulling_KeepsRealCorners`).

**한계:** 당기기는 꼭짓점을 **빼는** 연산이라 모퉁이의 진짜 꼭짓점을 새로 만들지는 못한다. 모퉁이를 비스듬히 질러가는 문 중심이 그대로 남아 꺾임이 실제보다 완만한 경우가 있다. 그래서 개선 폭이 예상(1 dB 안팎)보다 작은 0.2~0.3 dB에 그쳤다. 벽 모서리를 꼭짓점 후보로 넣는 본격적인 가시성 그래프는 비용이 훨씬 커서 하지 않았다.

### 3.11 에너지 히트맵 (6-3)
BODYCAM 영상의 출발점이 된 "복도를 타고 번지는 에너지" 그림을 게임 안에서 보여주는 디버그 표시.

기존 방식은 방마다 바닥 칸에 `DrawDebugSolidBox`를 찍는 것이었다. 방 하나가 단색이라 경계가 뚝 끊기고, 비용 때문에 칸을 3만 개로 솎아내야 해서 사이사이가 비었다.

대신 스캔 범위를 격자로 나눠 칸마다 "그 자리의 방 번호"를 미리 굽고(`UAcousticHeatmapVolume::Rebuild`), 매 틱(20 Hz) 방별 에너지 색을 **아틀라스 텍스처**에 채운다. Z 슬라이스를 타일로 펼친 2D 텍스처라 3D 텍스처 런타임 갱신 API에 의존하지 않는다. 스캔 범위를 덮는 **디퍼드 데칼**(`M_AcousticHeatmap`)이 화면에 보이는 표면을 그 지점의 에너지 색으로 칠한다.

색을 데칼 UV가 아니라 **표면의 월드 좌표**로 고르는 것이 핵심이다. 덕분에 투영 방향과 무관하게 늘어나지 않고, 바닥이든 벽이든 그 자리가 속한 방의 색이 칠해진다. 방 경계는 텍스처 보간(XY는 이중선형, Z는 두 슬라이스 lerp) 덕분에 부드럽게 이어진다.

포스트 프로세스 대신 데칼을 고른 이유: 포스트 프로세스에서는 씬 깊이로 월드 좌표를 되짚어야 하는데, 그 코드가 엔진 버전마다 달라지는 내부 심볼(LWC 처리 포함)에 의존한다. 데칼은 칠할 표면의 월드 좌표를 머티리얼 그래프에서 그대로 받으므로 그 위험이 없다.

| 항목 | 값 |
|---|---|
| 격자 해상도 | 스캔 격자를 XY 96 / Z 48칸 이하로 줄여서 사용 (예: 복도 씬 50 x 16 x 8 → 아틀라스 150 x 48) |
| 갱신 | 20 Hz, `UTexture2D::UpdateTextureRegions` |
| 콘솔 | `ors.Debug 1`로 켜고, `ors.Heatmap.Intensity`로 밝기 조절 (0 = 히트맵만 끔) |

**삽질 기록:** 데칼 도메인은 블렌드 모드가 제한된다(Translucent 계열만). 기본값인 Opaque로 두면 머티리얼 컴파일이 조용히 실패하고 **엔진 기본 머티리얼로 대체**되어, 파라미터를 아무리 바꿔도 화면이 똑같았다. 로그의 `Failed to compile Material ... Default Material will be used in game`에 원인이 그대로 적혀 있었다. 또 `DecalBlendMode`는 Python API에서 잠겨 있어 기본값(Translucent)을 그대로 쓰고, Unlit 셰이딩으로 Emissive를 Opacity만큼 얹는 방식을 택했다.

**한계:** 방 하나가 단색인 것은 그대로다(확산 음장 가정). 부드러워 보이는 것은 방 경계에서의 보간이지 방 안의 에너지 분포가 아니다. 방 안까지 보고 싶으면 `MaxRoomLength`를 줄여 공간을 잘게 쪼개야 한다.

### 3.12 백그라운드 재생성 (6-4)
스캔 → 방 분할 → 시뮬레이터 교체를 게임 스레드에서 한 번에 하고 있었다. 레벨 로드와 `ors.Rebuild` 때 그만큼 프레임이 통째로 멈춘다.

두 단계는 성격이 다르다.

| 단계 | 스레드 | 이유 |
|---|---|---|
| 격자 스캔 (오버랩 쿼리) | 게임 스레드 | 물리 씬을 읽으므로 워커 스레드로 옮길 수 없다 → 대신 **프레임마다 예산만큼만** 진행 (`FAcousticGridScanJob::Step`) |
| 방 분할 (`SegmentSpace`) | 워커 스레드 | 엔진에 의존하지 않는 순수 계산이라 격자만 넘겨 주면 된다 (`Async(EAsyncExecution::ThreadPool, ...)`) |

핵심은 **새 그래프를 따로 만들고 마지막에 갈아 끼운다**는 점이다(`ApplyNewGraph`). 재생성이 도는 동안 시뮬레이터는 이전 그래프로 계속 틱하므로 소리가 끊기지 않는다. 예전에는 `SegmentSpace`가 현재 그래프를 직접 덮어써서 시뮬레이터를 먼저 파괴해야 했다.

스캔 예산은 `AOrganicReverbVolume::ScanTimeBudgetMs`(기본 2 ms). 시간 확인 자체도 비용이라 256칸마다 한 번만 본다.

게임 모드 검증 (`ORS_DistantGunshot`, 69 x 42 x 9 = 26,082칸): 스캔 40.0 ms를 **19프레임에 나눠** 처리(프레임당 약 2 ms), 전체는 0.1초 만에 끝. 방 분할 6.5 ms는 워커 스레드. 예전에는 이 46.5 ms가 한 프레임에 몰렸다.

즉시 재생성이 필요한 곳(자동화 테스트, `RebuildAcousticGraph`)을 위해 한 번에 끝내는 `FAcousticGridScanner::Scan`도 남겨 뒀다. 예산 0을 주고 `Step`을 한 번 부르는 얇은 래퍼다.

**한계:** 히트맵 격자를 굽는 일은 아직 게임 스레드에서 한다(교체 직후 1회). 스캔 격자보다 훨씬 성긴 해상도라 비용이 작지만, 아주 큰 레벨에서는 이것도 워커로 옮길 여지가 있다.

### 3.13 방 사이 전달 지연 (6-5)
확산 방정식에는 전파 속도가 없다. 밀도차가 있으면 그 즉시 흐름이 생기므로, 총성이 난 순간 40 m 밖 방에도 (아주 작게나마) 에너지가 도달했다. 피크 순서는 맞지만 "멀리서 늦게 들린다"는 단서가 약했다.

포탈을 빠져나간 에너지를 바로 옆방에 넣지 않고 **지연 큐**에 담아 두었다가, `(방 중심 → 문 → 옆방 중심)` 거리를 음속으로 지나는 시간이 지난 뒤에 넣는다. 문을 경유한 거리라 ㄱ자로 꺾인 통로에서도 벽을 가로지르지 않는다.

**안정성이 관건이었다.** 지연이 있는 되먹임은 진동하기 쉽다. 받는 방의 에너지가 아직 안 올라왔는데 밀도차만 보고 계속 보내면 평형을 훌쩍 넘어간다 — v0 결함 3(명시적 오일러 발산)과 같은 종류의 함정이다. 두 가지로 막았다.

1. **가는 중인 에너지를 받는 쪽 밀도에 미리 더한다.** 이미 보낸 것을 또 보내지 않으므로 한 번에 평형까지만 보내고 멈춘다.
2. **보낼 수 있는 양을 방에 실제로 있는 에너지로 자른다.** 음수 에너지가 원천적으로 불가능하다.

에너지는 "방 안 + 가는 중"을 합쳐야 보존된다 (`GetTotalEnergy`가 둘을 더한다).

검증 (`Core_PortalDelay_*`):

| | 결과 |
|---|---|
| 34.3 m 떨어진 옆방 첫 도착 | 지연 없음 0.004 s → **지연 적용 0.100 s** (34.3 / 343 = 0.100 s) |
| 거대 포탈 + dt 0.001~2 s 반복 | 음수 0건, 에너지 증가 0건, 총량 3.000000 그대로 |
| 충분히 지난 뒤 | 가는 중 0, 밀도비 1.000 — 지연은 늦출 뿐 평형을 바꾸지 않는다 |

복도 전파(§4.2의 BODYCAM 히트맵)가 눈에 띄게 달라졌다. 전에는 5 ms에 이미 복도 끝까지 값이 찍혔지만, 이제는 파면이 실제로 번져 간다:

```
      t |    C0    C1    C2    C3    C4    C5    R1    R3    R5
 0.005s |    -0  -999  -999  -999  -999  -999  -999  -999  -999
 0.050s |    -3    -8   -32  -999  -999  -999   -29  -999  -999
 0.100s |    -5    -7   -13   -26   -61  -999   -19   -54  -999
 0.200s |    -8   -10   -12   -17   -23   -32   -17   -29   -51
```

옆방 피크도 뒤로 밀렸다: R1 145 → **183 ms**, R3 265 → **346 ms**, R5 397 → **517 ms**.

비용은 방 1000개 / 포탈 1997개 기준 틱당 80 → **145 µs**. 목표(1 ms)에는 여유가 있다. 소리가 있는 방이 몇 개뿐이라 대부분의 포탈은 큐가 비어 있고, 빈 큐는 건너뛴다.

**한계:** 가는 중인 에너지에는 흡음이 걸리지 않는다. 지연이 보통 수십 ms라 그동안의 감쇠가 작아서 무시했다.

#### 게임 모드 검증에서 발견한 결함: 분할된 공간의 잔향 길이
당시 테스트 맵 5종(현재 7종)을 `-game` 모드로 실행해 확인하던 중, `ORS_ClosetAndHall`의 20 m 홀이 `MaxRoomLength` 8 m 기준으로 18조각으로 나뉘면서 **조각마다 RT60이 10.5 ~ 26.9 s로 제각각**(정답 12.4 s)인 것을 발견했다. 조각 사이 분할면은 벽이 아니라 포탈이라 표면적에서 빠지므로, 가운데 조각은 바깥 벽이 거의 없어 Sabine 식이 비정상적으로 긴 값을 낸다. 에너지 시뮬레이션 자체는 물리적으로 맞지만(조각끼리 넓은 포탈로 에너지를 주고받음), 리스너 방의 **DecayTime 매핑**이 조각 단위라 홀 안에서 움직이면 잔향 길이가 요동친다.

**해결:** 세그멘터가 분할 전 영역을 `FRoom::GroupId`로 기록하고, `MapToReverbParams(Graph, Room, ...)`가 같은 그룹 전체의 ΣV, ΣS·α로 DecayTime·HF 비율·반사 지연을 계산한다. Wet(이벤트 에너지)은 여전히 조각 단위다.
콘솔 검증 `Seg_SplitSpace_SharesGroupDecayTime`: 30 m 홀 3×3 분할 → 조각 단독 13.4 ~ 20.0 s → 그룹 기준 16.11 s (홀 전체 Sabine 16.11 s와 일치).
게임 모드 재검증: `ORS_ClosetAndHall` 홀 18조각 모두 12.86 s, `ORS_Corridor` 복도 3조각 모두 2.69 s. 옆방·옷장은 각자 별도 그룹.

**남은 문제 (알려진 한계):** 인접한 방이 같은 위치에 재질이 다른 벽을 겹쳐 두면(테스트 레이아웃의 공유 벽), 칸 하나에 재질이 하나뿐인 격자로는 양쪽 면을 구분할 수 없다.
- 처음에는 오버랩 결과 순서대로 읽어 실행마다 달라졌다 (옷장 α 0.180 ↔ 0.200, 홀 Decay 12.40 ↔ 12.86 s).
- 5-1에서 "흡음이 큰 재질 우선"으로 결정적으로 만들었지만, 이번에는 공유 벽이 양쪽 방 모두에서 흡음재로 읽힌다. `ORS_MaterialComparison`의 콘크리트 방이 옆 카펫 방과의 공유 벽까지 카펫으로 계산되어 Decay 2.03 s → 1.43 s.
- **해결 (5단계):** 격자에 칸 **면(face)마다** 재질을 기록한다 (`FOccupancyGrid::FaceMaterials`, 필요할 때만 할당). 스캐너는 표면 칸의 공기 쪽 면마다 두께 5% 칸의 얇은 슬랩으로 다시 오버랩 테스트해 그 면에 붙은 마감재를 읽고, 세그멘터는 방이 바라보는 면의 재질을 쓴다. 테스트 레이아웃은 방 간격 50 cm에 벽 두께 25 cm로 벽이 겹치지 않게 나란히 세운다. 실제 레벨에서 벽 양쪽 마감재가 다른 경우에도 그대로 적용된다.
- 콘솔 검증 `Seg_SharedWall_PerFaceMaterials`: 공유 벽 한쪽 면만 카펫 → A 0.0300 (콘크리트 그대로), B 0.0517 (기대값 일치).
- 테스트 맵 재생성 후 게임 모드 검증: `ORS_MaterialComparison` 콘크리트 방 α 0.050 (콘크리트 벽 + 바깥 문, 계산값과 일치) → Decay **2.03 s로 복구** (1.43 s였음), 카펫 방 α 0.216. `ORS_ClosetAndHall` 옷장 α 0.200 (순수 카펫). 자동화 테스트 3개 통과.

관찰: 레이아웃 바깥 빈 공간(방과 방 사이 야외 공기)도 방으로 잡힌다 (예: 복도 씬 Room_0~3, α≈0.5~0.66). 포탈이 없어 시뮬레이션에는 영향이 없지만 디버그 표시가 지저분해지므로 5단계에서 "포탈 없는 바깥 영역" 필터를 검토한다.
